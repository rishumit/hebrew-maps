# ADR 0002 – אחסון וחיפוש: SQLite (R*Tree + FTS5) במקום PostGIS + Elasticsearch

**סטטוס:** התקבל · אוקטובר 2026

## הקשר
המסמכים ממליצים על PostgreSQL+PostGIS, ‏Elasticsearch ו-Redis (02-architecture, ‏06-deployment-ops). כל אלה מכוונים לפריסה בענן עם כמה שרתים. בפועל:
- הנתונים **לקריאה בלבד** ומתעדכנים בבנייה מחזורית (שבועית או חודשית), ולא בכתיבה שוטפת;
- היקף הנתונים: כ-100–200 אלף POI, כ-200 אלף רחובות ומאות אלפי כתובות, כלומר מאות MB;
- המערכת רצה על מחשב אחד. ‏Elasticsearch לבדו דורש 2GB+ זיכרון, ו-PostGIS דורש שירות נוסף, ניהול סכמות וכוונון.

## החלטה
קובץ SQLite יחיד (`maps.db`, בדומה ל-GeoPackage) עם:
- **R\*Tree** לשאילתות מרחביות (רדיוס, אריחים, גאוקודינג הפוך) ובדיקת point-in-polygon בקוד;
- **FTS5** עם tokenizer ו-prefix indexes, ומעליו **מנתח עברי משלנו**: נרמול (ניקוד, אותיות סופיות, גרשיים, כתיב מלא וחסר), אותיות השימוש (ב/ה/ו/ל/מ/ש/כ), קיצורים, טבלת trigram לתיקון שגיאות עם מרחק עריכה מותאם לעברית (ט/ת, כ/ק, ס/ש…), והמרת פריסת מקלדת;
- דירוג משוקלל: התאמת טקסט, חשיבות (סוג, ויקידאטה, גודל) ומרחק מהמפה או מהמשתמש;
- הצינור בונה קובץ חדש ומחליף אותו **אטומית**, והשרת טוען אותו מחדש אוטומטית (hot reload).

## השלכות
- ביצועים שנמדדו על 120 אלף POI: השלמה אוטומטית p95 ≈ 30ms, חיפוש p95 ≈ 90ms, כרטיס POI < 1ms. היעדים במסמך: 200ms ו-500ms.
- אין שרת מסד נתונים לתחזק. גיבוי הוא העתקת קובץ, וכל הבדיקות רצות בלי תשתית.
- **מגבלה:** כתיבה מקבילה (תרומת משתמשים, מחוץ לתחולה בשלב 1) תדרוש מעבר ל-PostgreSQL. הסכמה (`hmaps/core/db.py`) ושכבת הגישה ממודרות כך שהמעבר יהיה מקומי.
